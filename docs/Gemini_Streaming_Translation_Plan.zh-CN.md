# Gemini Live Translate 适配计划

日期：2026-09-05

状态：待实施。本次只改写计划，不修改应用代码。以下是实现设计与验收条件，不能视为真实服务验证结果。

## 1. 目标与方向

接入 `gemini-3.5-live-translate-preview`，直接从音频生成原文和目标语言译文，在桌面、紧凑模式和 VR Overlay 流式显示。对应目标直接采用 Live Translate 译文，不再调用 LLM 二次翻译。

在现有 Gemini Provider 下新增 `gemini_live_translate` 服务，与 `gemini_transcribe` 并列。复用已有 WebSocket、PCM 编码、凭证和字幕发布设施。原有 Transcribe 与文本翻译继续可选。

不实施旧计划中的临时原文重复翻译、预览调度器、限频机制或 `translation.live_preview` 开关。服务选择本身就是启用入口。

## 2. 已核实的能力与限制

Live Translate 支持连续音频翻译，同时开启输入、输出音频转写即可取得原文和译文。每个会话配置一个目标语言。它不支持文本输入或自定义指令，因此不能直接套用文本翻译的 Prompt、术语表指令或外部上下文。官方配置使用 `AUDIO` 输出；客户端不播放音频，并不代表服务端停止生成音频。[官方接入文档](https://ai.google.dev/gemini-api/docs/live-api/live-translate)

通用 Live API 说明输入转写独立发送，不保证与其他消息的顺序；输出转写在对应生成完成或中断标记前结束。文档没有为两路转写提供可直接配对句子的共同 ID。`turnComplete` 表示模型回合结束，不能单独证明对应原文也已到齐。[WebSocket 协议参考](https://ai.google.dev/api/live)

因此，流式双语显示可作为明确目标；逐句配对、历史记录和 OSC 输出还需要真实消息验证。不能把“能取得两路文字”当成“能够可靠逐句对齐”。

## 3. 配置与首版范围

### 服务入口

- 在现有语音服务选择器增加 Gemini Live Translate，默认模型为 `gemini-3.5-live-translate-preview`。
- 使用所选 Gemini 语音 API Profile 的凭证，由 Rust core 建立连接，不把凭证发送给网页。
- 模型配置进入现有 `asr.service_settings`，通过已有默认值补齐机制兼容旧配置；不自动改变用户已选服务。
- 不新增依赖、SDK、账号类型、环境变量、数据库表或独立功能开关。

### 目标语言与模式

每路音源只建立一个 Live Translate 会话，使用该音源目标列表的第一项作为直接翻译目标。麦克风、扬声器分别解析自己的列表，最多两路会话。界面明确标注第一目标由 Live Translate 处理。

已有第二、第三目标保留原有定稿后文本翻译，不删除配置，也不隐式创建额外音频会话。首版只有第一目标获得 Live Translate 的实时译文。

启用条件为自动翻译模式、有效 Gemini 语音 Profile、至少一个受支持的目标语言。当前翻译模式默认是 `disabled`，启动时必须检查；不满足时明确报配置错误，不静默切换模型或默选英语。运行中切到关闭或手动模式时停止该服务，并提示选择普通识别服务。

第一目标的 LLM Profile、文本模型和 thinking 设置保留，切回普通识别时继续使用。Live Translate 生效时界面显示这些字段不适用，后台不再要求第一目标具备有效 LLM 凭证。额外目标和手动文本翻译仍执行原有校验；Live Translate 不进入纯文本模型选择器。

目标来自运行时语言预设解析后的配置。改变第一目标、语音 Profile 或语音模型时重建会话；只修改额外目标的 LLM 参数不重启语音连接。

### 能力说明

界面说明第一目标不使用文本翻译 Prompt、术语表、thinking 和 VRCX 上下文。不将它们拼入不支持的 system instruction。源语言首版采用自动检测，不承诺强制源语言能力。

`echoTargetLanguage` 固定为 `false`，不增加设置项。输入已经是目标语言时允许没有译文，不将其报为无效响应；按已有同语言规则结束翻译等待。目标代码使用官方支持列表，覆盖 `zh-Hans`、`zh-Hant`，不擅自套用 Transcribe 的语言代码转换。

## 4. 数据路径与协议实现

```text
麦克风 / 扬声器
      |
      v
现有音频管线 -> 每路一个 Live Translate 会话
                         |
                 原文流 + 译文流
                         |
                         v
                 双语字幕生命周期
                   /           \
                  v             v
          桌面 / 紧凑 / VR   经验证的定稿结果
                                |
                                v
                        历史记录 + 现有 OSC
                                |
                                v
                         额外目标文本翻译
```

1. 新增专用适配分支及 `provider/gemini_live_translate.rs`，复用 Gemini 请求地址、音频编码和连接循环。保留 Transcribe 既有归一化语义。
2. 使用官方 Live Translate WebSocket 示例的 setup：`generationConfig` 内配置 `responseModalities: [AUDIO]`、输入/输出转写及 `translationConfig`。通用参考和专用示例的字段层级不同，应以专用接口契约测试验证；不在运行时自动轮试多种 setup。
3. 收到 `setupComplete` 后发送音频。复用已有 Text/Binary JSON、Ping/Pong、服务端错误和关闭原因处理，不能把明确服务错误统一改成确认超时。
4. 使用已有 16 kHz 单声道 PCM16，以约 100 ms 块发送；仅在现有块大小不合适时增加小缓冲，不能等整句录音完成。
5. 采用持续发送的会话路径，避免沿用 Transcribe 每次本地 VAD 结束就提交一句的语义。普通停顿继续接收；停止音源才发送 `audioStreamEnd` 并有界排空。
6. 返回音频不解码播放、不缓存、不转发给前端，但必须继续处理同一消息中的文字和状态。合法音频、用量或等待输入消息没有文字时不报无效响应。

## 5. 双语状态、分段与取消

### 实时事件

每路维护会话代次、当前显示块，以及原文和译文各自的累积状态。哪一路先到就更新哪一路；译文先到时允许先显示译文，不能要求原文气泡已经存在。

当前归一化接口一次只返回 `Option<CloudEvent>`。新增一个包含双语快照及状态的内部事件，一次处理同一消息中的全部文字和完成标记，避免早返回丢掉另一路内容。无需为所有 Provider 重构成事件集合框架。

领域事件使用 `translation.live_updated`，桌面映射为 `live_translation_updated`。负载包含会话代次、显示块 ID、源/目标语言、原文、译文及 `partial`、`completed`、`cancelled` 状态，不依赖数据库字幕 ID。完整快照使前端采用替换更新；旧会话及已终结块的迟到事件被拒绝。

协议增量采用拼接，明确的快照采用替换。不得按文字前缀猜测消息类型，也不能把正常重复词当作重复消息删除。增量语义须通过实际消息样本固化为回放测试。

### 定稿的关键约束

- 不按消息序号、标点数量或固定延时配对两路文字。
- 不将每条 `inputTranscription` 当成完整双语句子。
- `generationComplete` 只能证明输出生成结束；输入归属必须单独成立。
- 未经验证的显示块边界只用于实时显示，不用于写入“已完成翻译”。

最脆弱的前提是实际模型消息能提供可靠的双语块边界。本轮没有真实会话样本，官方文档不足以证明严格逐句对应。实施者须以连续两句话、长句、晚到原文和中断的真实消息回放验证边界，再开放历史配对与 OSC。这是协议验收门槛，不能用理想顺序的模拟测试替代。

如果边界无法可靠确认，保留独立双语流显示用于验证，但不发布为完整适配，不自动保存配对译文；报告限制后再决定是否接受更粗粒度的记录。不得临时增加 LLM 对齐器或猜测延迟来掩盖问题。

### 停止、错误和重连

停止后最多排空 5 秒，可信完成边界允许提前结束；超时不算正常完成，未完成译文不保存为成功。排空期间同时消费事件，避免有界 channel 在等待任务退出时堵塞。

断线、中断、配置切换终结当前显示块。沿用已有有界重连策略，新连接使用新会话代次，不回放旧音频、不恢复旧块、不增加第二套重试。`goAway` 进入同一连接关闭和重连路径。只含音频的响应不会触发该路径。

每路只维护有限当前状态，复用已有转写长度上限；达到上限时报错并终结，不能静默截断后保存为完整翻译。

## 6. 存储、其他目标与 OSC

通过分段验收后，原文和译文分别写入既有字幕表、翻译表，译文记录实际 Provider 和模型。当前 `add_subtitle` 会清空返回对象中的 translations，不能仅在 `Subtitle` 中附上译文就认为已经保存；必须调用现有翻译写入接口。

先确认原文存储成功，再保存译文，最后发布翻译完成事件。第一目标不进入 `TranslationDispatcher`；第二、第三目标只按定稿原文排队一次。使用既有 message ID 关联机制，不创建另一套历史记录模型。

原文保存成功但译文写入失败时保留原文并报告存储失败，不发布成功，也不自动调用 LLM。原文被过滤、回声过滤或为空导致整块取消时，其译文不能绕过过滤单独发布。

临时双语事件只发往显示端，不发送 OSC。完整且保存成功的双语结果走现有翻译完成路径，第一目标保持首选目标，沿用现有格式和节奏。同语言场景允许仅发送原文，不永久等待不存在的翻译。

## 7. 显示行为

- 桌面和紧凑模式在同一块中独立更新两路文本，原文刷新不清空译文。
- VR Overlay 复用已有临时原文、临时译文选项，不增加一套开关。
- 以同一显示块 ID 转换成已保存字幕，避免重复气泡或重新触发第一目标翻译。
- 停止超时、断线、取消和切换清理临时内容，保留既有历史。

## 9. 验证与验收

自动化测试覆盖：

1. 旧配置补齐新服务但不改变选择；模式、目标、Profile 校验正确。
2. setup 参数与目标正确；Text/Binary 确认、明确错误、Ping/Pong 和关闭原因正确处理。
3. 同一消息含音频、两路文字和结束标记时均不丢失；无文字音频不报错。
4. 真实消息回放覆盖两路先后顺序、重复词、连续句子、长句、晚到原文和中断，验证定稿边界。
5. 两路音源隔离，旧会话不覆盖新会话；修改第二目标不重启语音。
6. 第一目标无 LLM 调用，额外目标只调用一次；无效模式不隐式开音频翻译。
7. 存储成功才发布完成；失败、过滤和同语言不会错误发送 OSC 或永久等待。
8. 停止、channel 满、排空超时和重连不死锁，不保存截断译文。
9. 三种显示入口支持译文先到、原文更新、定稿转换和取消，尊重 VR 选项。
10. Transcribe 和其他服务的现有行为不回归。

验证命令：

- `cargo test --manifest-path core/Cargo.toml --lib`
- `npm --prefix apps/desktop test`
- `npm --prefix apps/desktop run build`
- `cargo test --manifest-path apps/desktop/src-tauri/Cargo.toml --lib vr_overlay::presentation`

真实验收需要现有 Gemini API Key 具有该预览模型的访问权限和可用配额。测试英译中、日译中、繁体目标、同语言、中途改口、连续说话、背景噪声、两路输入、停止及切换目标。记录首段原文/译文延迟、配对结果、会话数及可获取的用量；不预先承诺延迟或费用数字。

通过标准：说话过程中出现两路文字，保存的双语块不串句，第一目标无额外文本翻译调用，停止或重连无旧结果回流。分段未证明时，不把显示成功当作完整验收通过。

本轮已核对本地代码及可访问的官方文档，未发送付费语音请求。访问权限、实际字段行为、分段和延迟仍需实测。

## 10. 简化与回退

每路一个会话直接提供原文和首目标译文，避免同时运行第二条 Transcribe 流和重复调用 LLM。首版不增加多目标音频扇出、语音播放、自动模型降级、语义对齐服务或无缝恢复。

切回 Transcribe 即恢复识别后文本翻译，保留的 LLM 配置继续生效，历史数据无需迁移。回退软件版本前先切回旧服务，避免旧版本遇到未知服务 ID。

主要风险为实际分段契约和音频输出成本。前者通过真实回放及完整功能验收门槛控制，后者在服务选择处说明；不以猜测配对或叠加重试换取表面成功。
