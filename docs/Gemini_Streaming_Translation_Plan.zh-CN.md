# Gemini Live Translate 适配计划与实现

更新日期：2026-09-06

## 当前行为

在 Gemini Provider 下选择 `gemini_live_translate`，模型为 `gemini-3.5-live-translate-preview`。每路音源建立一个连续会话，第一目标由 Live Translate 直接翻译，额外目标使用既有文本翻译流程。

- 自动翻译模式下启用；第一目标不要求配置 LLM，也不调用 LLM 二次翻译。
- 麦克风、扬声器分别使用语言预设解析后的第一目标。目标、语音 Profile 或模型变化时重建相关连接。
- 原文和译文实时显示于桌面、紧凑模式与 VR；显示文本最多保留 160 个 Unicode 字符。
- 句末标点结束的原文与译文按到达顺序配对，完整文本写入既有历史记录。显示裁剪不影响存储。
- 原文保存后写入 Gemini 译文，记录实际 Provider 和模型，再发布完成事件。额外目标按完整原文排队一次，保持非首选。
- 完成结果进入既有 OSC 输出流程，遵循已有开关、音源、目标策略、格式和发送节奏。临时字幕不发送 OSC。
- 停止时发送 `audioStreamEnd`，最多排空 5 秒，再保存已收到的尾句。缺少译文时保留原文并报告翻译未完成，不把空译文标为成功。
- 同语言输入按既有语言比较规则识别；原文完成后无需等待被 `echoTargetLanguage: false` 省略的译文。
- 中断会清空未完成内容；重连使用新字幕 ID，不把两次连接中的句子相互配对。

## 分段规则与限制

原文和译文在独立缓冲区累积。句末使用 `。！？.!?` 和换行；英文句点检查后续分隔符，并避开分块传输中的小数。收到两边完整句子后逐对消费，一次响应可以形成多条记录。

这是一种按标点和顺序配对的规则，不是 Gemini 返回的共同句子 ID。模型合并或拆分句子、缩写及不同语言标点习惯可能造成配对偏差；目前不增加 LLM 对齐器、延迟猜测或逐句重连。

每路尚未配对的完整文本仍有 64 KiB 上限。达到上限时明确终止并报告错误，避免无限占用内存。断线前已经保存的历史保留；未配对数据不跨连接恢复。只有译文而没有对应原文的剩余文本不会创建独立历史条目。

## 存储与失败处理

复用现有字幕表和翻译表，不新增数据库结构或依赖。译文写入失败时保留原文、报告失败，不发布翻译成功，也不自动调用 LLM 补译第一目标。原文为空或被回声过滤时，整条结果不进入存储和 OSC。

第一目标的原有 LLM 配置保留，切回 Transcribe 时恢复使用。Live Translate 不使用文本 Prompt、thinking 或外部上下文；客户端不播放返回音频，但服务端仍会生成音频并按服务规则计费。

## 协议依据

Live Translate 采用连续处理，不保证每句话返回 `turnComplete`。真实合成语音样本已确认两路文本按增量返回；音频结束后等待 35 秒未观察到共同完成标记，因此不依赖该标记分段。[官方文档](https://ai.google.dev/gemini-api/docs/live-api/live-translate)

实际握手配置：`inputAudioTranscription` 和 `outputAudioTranscription` 位于 setup 根层；`responseModalities: [AUDIO]` 和 `translationConfig` 位于 generationConfig。专用文档的 WebSocket 示例将转写配置放在错误层级，真实服务会拒绝；当前实现与官方 SDK 映射及成功握手一致。[官方 SDK](https://github.com/googleapis/python-genai/blob/main/google/genai/_live_converters.py)

输入沿用 16 kHz 单声道 PCM16 和现有 WebSocket 连接处理。返回音频不播放、不缓存，但同一消息的转写文本仍会处理。

## 验证范围

自动化验证覆盖真实响应回放、先后顺序、完整长句与显示裁剪隔离、停止尾句只保存一次、缺少译文、同语言、中断清理、原生译文持久化、存储失败以及额外目标不成为首选。既有核心、前端及 VR 展示检查用于验证受影响入口。

真实服务测试确认了握手及英译中增量。新的历史记录及 OSC 行为仍需通过桌面音频采集和实际 VRChat 使用验收，不能将模拟测试等同于设备验收。
